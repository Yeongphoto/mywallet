# 공유 장부 생성·초대 설계

작성: 2026-10-14 · 브랜치: `android_dev`

현재 구현 업데이트: 격리된 테스트 배포에 공유 장부 생성·이름 변경·개인 클라우드 장부 복사/빈 장부·소유 한도·진행률·재개·장부 선택·초대를 추가했다. 실제 구조와 검증은 [공유 장부 생성 테스트](android-shared-creation-test.md)를 따른다. 아래의 단일 장부 구현 상태와 구현 예정 표기는 이전 설계 이력이다.

**최신 사용자 확인:** 현재 기록은 아직 공유하지 않은 개인 장부다. 아래의 기존 원본을 첫 공유 장부로 삼는 설명은 이전 설계 이력이다. 현재 앱 테스트는 웹 DB에서 분리한 개인 장부 복사본으로 전환하며, 이 개인 장부에서 새 공유 장부를 만들고 복사하거나 빈 장부로 시작한다. 개인 장부는 소유 공유 장부 1개 한도에 포함하지 않는다. 현재 상태와 검증은 [격리된 개인 장부 테스트](android-personal-test.md)를 따른다.

사용자 요청: 현재 웹앱과 Android에서 사용하는 기록을 첫 공유 장부로 삼는다. 기존 웹앱 사용에 영향을 주지 않고 개발한 뒤 웹앱에도 장부 선택·Google 로그인·초대 기능을 반영한다.

이 문서는 전체 구현 설계다. 2026-10-14 후속 요청으로 기존 하나의 공유 장부에 대한 Gmail 초대 생성·확인·수락·취소·참여자 제거와 테스트 APK를 구현했다. 새 장부 생성과 장부별 금융 테이블은 후속 단계다. 운영 DB 변경, 실제 상대방 초대·전송, 웹앱 배포는 아직 실행하지 않았다. 테스트 실행 방법은 [초대 테스트 APK](android-invitation-test.md)를 따른다.

같은 날 추가 요청으로 PC 없이 사용하는 HTTPS 테스트 서버와 별도 인증 DB를 배포했다. 로그인한 계정의 받은 초대는 첫 가계부 화면의 팝업으로 표시한다. 초대 ID로 수락하더라도 대상 계정·유효기간·권한을 서버에서 확인하며, 링크나 관리 페이지를 먼저 표시하지 않는다. 기존 운영 금융 DB·웹앱 배포는 유지한다.

## 확정한 생성 정책 (2026-10-14 후속 요청)

- 공유 장부 생성은 Google 로그인 계정만 가능하다. 계정당 소유자(owner)로 보유하는 공유 장부는 최대 1개다. 개인 장부와 초대받아 참여하는 장부는 이 생성 한도에 포함하지 않는다.
- 현재 기록은 개인 장부로 분류하므로 소유 공유 장부 한도에 포함하지 않는다. 기존 웹의 기록은 유지하고 격리된 개인 장부 복사본에서 공유 장부를 생성한다. 이전 테스트의 공유 메타데이터를 실제 소유 공유 장부로 계산하지 않는다.
- 새 공유 장부의 시작 방식은 `개인 장부 복사하기` 또는 `빈 장부로 시작하기`다. 개인 장부는 본인의 로컬 장부 또는 향후 구현할 개인 클라우드 장부이며, 다른 공유 장부의 복사는 첫 버전에서 제외한다.
- 복사는 생성 시점의 독립된 기록이다. 개인 원본은 보존하고 이후 개인 장부와 공유 장부 사이에는 자동 동기화를 하지 않는다. 참여한 기기들은 같은 공유 장부 ID의 원격 데이터를 함께 사용한다.
- 장부 이름은 필수다. 앞뒤 공백을 제거한 뒤 사용자에게 보이는 문자 기준 1~30자로 제한하고, 소유자가 변경할 수 있다. 이름은 계정 간 중복 가능하며 식별·권한 판단에는 UUID를 사용한다.
- 소유 장부가 있으면 관리 화면에 해당 장부와 이름 변경·초대·참여자 관리를 표시한다. 다시 만들기 버튼 대신 기존 장부를 관리하도록 한다. 다른 사람의 초대를 수락하는 것은 허용한다.
- 이 절의 개인 클라우드·새 장부 생성·한도·이름 변경은 구현 예정 정책이다. 현재 배포본은 고정된 첫 공유 장부의 초대만 지원한다. 개인 동기화 연결·해제와 공유 장부 연결 끊기는 별개의 동작으로 설계한다.

## 1. 현재 구조와 적용 방향

현재 `ledgers`, `ledger_memberships`, Google 사용자 UUID 및 권한 검사 기반이 있다. 개발 서버의 `/api/wallet/context`는 지정된 하나의 장부 UUID를 반환한다. Android는 이 UUID와 사용자 UUID로 캐시를 구분한다.

현재 금융 테이블과 기존 웹 `/api/data`는 단일 장부 구조다. 금융 테이블에 새 장부 행을 섞으면 기존 웹의 전체 조회에 노출될 수 있다. 장부 ID를 화면에 추가하는 것만으로 다중 장부가 완성되지는 않는다.

초기 구현은 다음 두 저장 경로를 같은 장부 인터페이스로 제공한다.

| 장부 | 실제 저장 경로 | 기존 웹과의 관계 |
| --- | --- | --- |
| 현재 기록을 사용하는 첫 공유 장부 | 기존 D1 금융 테이블 | 기존 웹이 쓰는 원본을 그대로 사용 |
| 새로 생성하는 장부 | 새 장부별 금융 테이블 | 기존 웹의 전체 조회에 섞이지 않음 |

새 장부 테이블은 예를 들어 `ledger_transactions`, `ledger_assets`처럼 별도 이름을 사용한다. 기존 금융 테이블에 `ledger_id`를 추가하고 기존 핸들러를 일괄 수정하는 방식은 초기 단계에서 사용하지 않는다. 새 장부의 기준 저장소도 원격 D1이며 별도 로컬 캐시가 기준이 되지 않는다.

## 2. 장부 ID와 현재 기록 연결

- 장부의 내부 ID는 서버가 발급하는 UUID다. 장부 이름을 바꾸거나 초대 링크를 재발급해도 ID는 변하지 않는다.
- 현재 개발 연결에 이미 있는 장부 UUID를 확인하고 유지한다. 운영 등록 시에는 같은 ID의 중복·다른 소유권 여부를 확인한다. 접속할 때마다 새 ID를 만들지 않는다.
- 현재 기록은 새 DB로 복사하지 않는다. 서버의 저장 경로 매핑으로 첫 공유 장부와 기존 금융 테이블을 연결한다. 거래·자산·정기 규칙·카드 결제 ID, revision, operation 결과, 동기화 cursor를 유지한다.
- 첫 장부의 소유자는 이미 Google 로그인으로 확인한 본인 사용자 UUID다. 상대방 권한은 초대 수락 시 별도 생성한다. 첫 가입자나 이메일 문자열만으로 기존 기록의 소유자를 정하지 않는다.
- ID는 장부를 식별할 뿐 접근권한을 주지 않는다. ID 입력만으로 다른 사람의 기록을 열 수 없다.
- 설정의 장부 관리에서 전체 ID를 확인·복사할 수 있지만 일반 장부 선택에는 장부 이름을 표시한다. 별도의 짧은 참여 코드는 첫 버전에 넣지 않는다.

현재 장부의 등록은 소유자와 원본 저장 경로를 명시한 관리용 작업으로 한 번만 실행한다. 일반 `장부 만들기` API가 기존 기록을 가져가거나 기존 장부에 임의로 자신을 owner로 등록하게 만들지 않는다.

## 3. 장부 생성 흐름

### 현재 기록

`본인 Google 계정 확인 → 기존 장부 UUID 등록·원본 연결 → 공유 장부 목록에 표시 → 상대방 초대`

기존 기록을 사용하는 첫 장부는 이 경로로 준비한다. 여자친구는 웹 전환 전까지 현재 웹앱을 그대로 사용하고, 앱 참여 권한은 초대로 추가한다.

### 새 장부

`Google 로그인 → 장부 만들기 → 이름 입력 → 시작 방식 선택 → 서버 UUID 발급 → 소유자 등록 → 장부 열기`

시작 방식은 `빈 장부로 시작하기`와 `개인 장부 복사하기`다. 개인 장부 복사는 원본 선택·이름·복사할 기록의 범위를 확인한 뒤 실행한다. 본인이 회원인 다른 공유 장부의 기록을 자동 복사하는 기능은 첫 버전에서 제외한다.

서버가 기존 소유 공유 장부를 확인하고 계정당 1개 제한을 적용한다. 화면에서 버튼을 숨기는 것만으로 제한하지 않는다. 동시 요청·다른 기기·재시도에도 2개가 생성되지 않도록 DB의 소유 공유 장부 고유 제약과 생성 operation ID를 함께 사용한다. 이미 소유한 장부가 있다면 기존 장부로 안내하고 새 원본 복사를 시작하지 않는다.

빈 장부는 메타데이터·owner membership·기본 설정을 원자적으로 생성한다. 같은 생성 요청을 재시도하면 같은 장부를 반환하도록 생성 operation ID를 사용한다.

로컬 기록으로 시작하면 장부를 먼저 생성한 후 명시적인 가져오기를 수행한다. 가져오기 작업의 원본·대상 ID·매핑·진행 위치를 저장하고 기존 재시도 방식을 유지한다. 실패하면 원본을 보존하고 같은 새 장부로 이어서 진행하며 재시도마다 장부를 추가 생성하지 않는다. 완료 전 다른 사람에게 해당 장부를 초대하지 않는다.

복사 중인 장부도 소유 한도에 포함한다. 중단 시 관리 화면에서 같은 작업을 재개한다. 거래·자산·계획·사용자 카테고리·정기 규칙·삭제된 정기거래 ID·카드 결제 등 금융 기록과 참조를 일관된 원본 시점으로 복사한다. 개인 테마·로그인 세션·멤버십·초대·동기화 cursor·operation 이력은 새 장부의 공유 데이터로 복사하지 않는다. 정기기록은 복사 이후 각 장부에서 독립적으로 작동한다. 클라우드 원본에 보류 변경이 있으면 먼저 저장 결과를 확인한 뒤 서버 revision을 기준으로 복사하며, 미완료 상태를 최신 원본으로 간주하지 않는다.

기존의 시간 지정 정기기록 가져오기 제한을 숨기지 않는다. 새 장부 저장 경로에 시간 지원과 회귀 검증을 구현한 뒤에만 지원 범위를 확장한다. 기존 장부 API에 대한 제한은 유지한다.

## 4. Google 계정 초대

권장하는 첫 버전은 **계정을 지정한 초대 링크**다. 앱이 이메일을 자동 발송하는 기능은 별도 메일 서비스가 필요하므로 먼저 링크 복사·휴대폰 공유 기능을 제공한다. 링크를 발급하는 것과 상대방에게 메시지를 전송하는 것은 별개다.

1. 소유자가 장부 관리에서 `초대`를 누른다.
2. 상대방의 Google 로그인 이메일과 권한을 입력한다. 기본 권한 제안은 `함께 기록하기(editor)`이며 `보기만(viewer)`도 선택할 수 있다.
3. 서버가 owner 권한을 확인하고 만료되는 1회용 초대를 만든다. 첫 버전의 만료 제안은 7일이다.
4. 소유자가 링크를 복사해 카카오톡 등으로 직접 전달한다. 실제 자동 전송은 하지 않는다.
5. 상대방이 링크를 열고 지정한 Google 계정으로 로그인한다. 설치 전에는 HTTPS 초대 페이지를 사용하고, 앱 내부 초대 화면도 같은 서버 검증을 사용한다. Android App Link 연결은 별도 검증 항목이다.
6. 장부 이름·초대한 사람·권한을 확인하고 `참여`를 누른다. 링크 GET이나 로그인 성공만으로 참여시키지 않는다.
7. 서버가 대상 계정·만료·취소 여부를 확인하고 초대 소비와 membership 생성을 한 트랜잭션으로 처리한다. 이후 장부 목록에 나타난다.

다른 계정으로 열면 `초대받은 계정으로 로그인`을 표시한다. 링크가 전달돼도 지정한 계정이 아니면 참여할 수 없다. 이미 참여한 본인이 동일한 수락 요청을 재시도하면 성공 상태를 반환하고, 다른 사용자가 재사용하면 거부한다.

장부 UUID와 초대 토큰은 구분한다. 토큰은 충분한 무작위 값으로 만들고 DB에는 해시만 저장한다. 만료·사용·취소 상태를 서버에서 검사한다. 재발급하면 기존 미수락 링크를 취소한다. 토큰을 금융 요청에 쓰거나 장기 접근권한으로 사용하지 않는다.

초대 URL은 서버의 고정 HTTPS origin으로 만든다. 토큰은 fragment로 전달하고 초대 화면이 읽은 직후 주소에서 제거한다. OAuth 이동 전에 서버의 짧은 수명 초대 교환 세션으로 보관한다. URL·분석 로그·외부 자원 Referer에 토큰을 남기지 않는다. 초대 페이지에는 외부 광고·분석 코드를 넣지 않는다.

### 계정 판정

로그인 계정의 기준은 현재처럼 Google의 검증된 `(issuer, sub)`와 내부 사용자 UUID다. 이메일은 초대 대상 확인용이며 사용자 병합이나 장부 소유권 키로 쓰지 않는다. 현재 코드에서는 이메일을 검증 결과로 읽지만 DB에 저장하지 않으므로 대상 확인용 프로필 확장이 필요하다.

Gmail과 검증된 Google Workspace 이메일을 우선 지원하는 설계다. 외부 이메일로 만든 Google 계정은 `email_verified`만으로 현재 이메일 소유권을 보장할 수 없으므로 별도 이메일 확인 또는 소유자의 계정 확인 후 승인이 필요하다. 외부 이메일까지 자동 수락하는 기능은 첫 버전에 넣지 않는다. Google의 계정 검증 기준은 [서버에서 Google ID 토큰 검증](https://developers.google.com/identity/sign-in/android/backend-auth)을 따른다.

수락 시 최근 Google 인증으로 대상 이메일과 권한 근거를 재확인한다. 서버가 확인한 이메일을 최소한으로 보관하고 Gmail의 점·별칭을 임의로 제거하거나 계정을 자동 병합하지 않는다. 초대 토큰의 수명·1회 사용 설계는 [OWASP의 토큰 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)을 참고한 적용안이다.

## 5. 권한과 연결 끊기

| 역할 | 조회 | 거래·자산 등 기록 변경 | 초대·멤버 관리 |
| --- | --- | --- | --- |
| 소유자(owner) | 가능 | 가능 | 가능 |
| 함께 기록(editor) | 가능 | 가능 | 불가 |
| 보기만(viewer) | 가능 | 불가 | 불가 |

장부에는 소유자 1명을 둔다. 소유자는 초대 취소·참여자 제거·editor/viewer 변경을 할 수 있다. 소유권 이전·장부 영구 삭제는 첫 버전의 일반 메뉴에 포함하지 않는다. 소유자는 소유권 이전 없이 장부에서 탈퇴할 수 없다.

다음 동작은 분리한다.

- **연결 끊기:** 이 기기에서 로컬 장부로 전환한다. Google 로그인과 공유 membership은 유지한다. 다시 선택하면 공유 장부를 열 수 있다. 현재 구현의 동작을 유지한다.
- **장부에서 나가기:** 소유자가 아닌 참여자가 자신의 membership을 제거한다. 공유 데이터는 삭제하지 않는다. 다시 참여하려면 새 초대가 필요하다.
- **참여자 제거:** 소유자가 해당 계정의 membership을 제거한다. 상대방의 이후 서버 요청은 거부한다.

권한은 매 서버 요청에서 확인하고, 쓰기 트랜잭션에도 membership 조건을 포함해 조회와 실제 저장 사이에 권한이 해제되는 경우를 막는다. 권한 상실 시 앱 화면을 숨기고 해당 장부의 금융 요청을 잠근다. 별도 오프라인 복사본까지 원격으로 지울 수 있다고 보장하지 않는다.

보류 변경·캐시는 기존 사용자/장부 namespace를 유지한다. 연결 끊기로 보류 데이터를 다른 장부에 전송하지 않는다. 나가기 전 보류 쓰기가 있으면 먼저 완료하거나 로컬 백업을 선택하도록 하며, 접근이 이미 철회됐으면 업로드하지 않고 복구 후보로 별도 보관한다.

## 6. 추가 데이터 모델

기존 인증·장부 메타데이터 구조는 유지하며 아래 확장을 제안한다. 구체 SQL은 격리 DB에서 검증한 뒤 마이그레이션 파일로 만든다.

| 구조 | 주요 필드·제약 |
| --- | --- |
| `ledgers` | 기존 UUID, owner 사용자 UUID, 이름, 생성 시각, 개인/공유 종류, 생성·복사 상태; 공유 장부에 한해 owner 고유 제약 |
| `ledger_memberships` | 기존 `(ledger_id, user_id)` 고유 관계, role; last-owner 제거 금지 |
| `ledger_storage_bindings` | `ledger_id`, `kind: legacy-default/scoped`; 기존 원본 연결은 1개만 허용, 서버 전용 |
| `ledger_invitations` | 초대 UUID, 장부 ID, 초대자, 대상 이메일, role, token_hash, 만료, 수락자·수락 시각, 취소 시각 |
| `auth_identity_profiles` | 검증된 issuer/sub 관계의 이메일, Google의 이메일 권위 여부, 마지막 인증 시각 |
| `ledger_creation_operations` | 요청자 UUID + 생성 operation ID 고유 관계, 생성 장부 ID, 요청 해시 |
| `ledger_audit_events` | 생성·초대·수락·취소·권한 변경·나가기; 원시 토큰과 금융 본문 저장 금지 |

초대는 pending → accepted / revoked / expired로 전환한다. 만료는 현재 서버 시각으로도 판정한다. 한 대상의 중복 pending 초대와 동시 수락을 처리하며 membership 고유 제약을 유지한다. 초대 생성·수락에는 요청 제한과 Origin 검사를 적용한다. 초대 결과에서 앱 가입 여부를 노출하지 않는다.

새 금융 저장 경로에는 거래·자산·계획·사용자 카테고리·설정·정기 규칙·삭제된 정기거래·카드 결제·operation 결과·sync 변경·sync group을 모두 장부 범위로 만든다. 거래만 분리하고 자산이나 설정은 공용으로 남기지 않는다.

- 일반 행의 키: `(ledger_id, id)`; 설정: `(ledger_id, key)`.
- operation 결과: `(ledger_id, operation_id)`; group: `(ledger_id, group_id)`.
- 모든 자산·이체·정기·카드 참조가 같은 장부에 속하는지 확인한다.
- 모든 조회·수정·삭제·백업·증분 응답에 장부 조건을 적용한다.
- cursor가 전역 증가값이어도 반환 행과 최대 범위는 선택 장부로 필터링한다. 클라이언트 cursor는 장부별로 보관한다.
- D1 기준·revision 충돌·operation 재시도·전체 snapshot 덮어쓰기 금지 원칙을 유지한다.

## 7. API와 기존 웹 호환

| 경로 제안 | 역할 |
| --- | --- |
| `GET /api/ledgers` | 로그인한 사용자의 참여 장부 목록 |
| `POST /api/ledgers` | 빈 장부 생성, 생성 operation ID 포함 |
| `PATCH /api/ledgers/:id` | owner의 장부 이름 변경, 서버에서 이름 검증 |
| `GET /api/ledgers/:id/context` | 선택한 장부 권한 확인 |
| `GET/PATCH /api/ledgers/:id/data` | 권한 확인 후 장부 저장 경로에 전달 |
| `GET /api/ledgers/:id/members` | 본인이 참여한 장부의 참여자 표시 |
| `POST /api/ledgers/:id/invitations` | owner의 대상 계정 초대 링크 발급 |
| `DELETE /api/ledgers/:id/invitations/:inviteId` | owner의 초대 취소 |
| `POST /api/invitations/exchange` | 원시 토큰을 짧은 수명 초대 교환 세션으로 교환 |
| `POST /api/invitations/accept` | 최근 Google 인증·명시적 수락 후 membership 등록 |
| `PATCH/DELETE /api/ledgers/:id/members/:userId` | owner의 참여자 권한 변경·제거 |
| `POST /api/ledgers/:id/leave` | 비소유자의 탈퇴 |

새 API는 인증 세션과 서버 membership을 사용한다. body의 사용자 ID·owner ID·role을 신뢰하지 않는다. `ledger_id`를 바꾸어 다른 장부에 접근하는 요청을 차단한다.

기존 웹 `/api/data`와 루트 화면·저장 키는 유지한다. 기존 원본 장부 adapter는 같은 서버의 기존 데이터 핸들러를 권한 검사 뒤 호출한다. 출시 구현에서 공개 인터넷 API를 프록시하는 현재 개발 bridge를 영구 구조로 삼지 않는다.

새 장부 데이터는 새 테이블에만 기록하므로 기존 웹이 새 장부를 조회하거나 지우지 않는다. 기존 장부는 기존 API와 새 인증 API가 같은 원본에 읽고 쓴다. 별도 복사본을 양방향 동기화하거나 두 DB를 동시에 쓰지 않는다.

**호환 기간의 한계:** 기존 웹의 익명 API를 그대로 유지하는 동안 해당 기존 장부가 초대받은 계정에게만 접근 가능한 상태가 된다고 말할 수 없다. 새 앱 API에는 회원 권한을 적용해도 이전 웹 경로의 접근 방식은 남는다. 다른 새 장부는 이전 API에 연결하지 않는다. 기존 장부의 접근까지 완전히 제한하는 시점은 여자친구의 Google 참여를 확인하고 웹도 인증 경로로 전환한 이후다.

여러 장부 지원 시 `/api/wallet/context`의 고정 장부 선택을 장부 목록·명시적 선택으로 바꾼다. 현재 장부 UUID의 캐시는 유지하며 루트 웹의 `mywallet:*`를 로그인 계정 캐시로 자동 복사하지 않는다. 전환 중 요청은 선택 당시의 장부 context에 고정하고 응답이 다른 장부 화면에 적용되지 않게 한다.

## 8. 앱 화면

설정의 같은 한 줄 컨트롤을 유지한다. 장부 선택에는 `로컬 장부`와 참여 중인 장부 이름을 표시한다. 공유 장부에서는 `연결 끊기`, 로컬에서는 `연결`을 표시한다.

장부 관리 화면에는 내가 소유한 공유 장부와 초대받아 참여한 장부를 표시한다. 소유 장부가 없을 때만 `공유 장부 만들기`를 제공하고, 생성 화면은 이름 입력과 두 시작 방식으로 구성한다. 소유자에게만 이름 변경·초대·권한 변경 메뉴를 노출한다. 장부 ID는 관리 화면의 복사 항목으로 둔다. 로그인과 공유 참여·개인 장부 복사를 별도 실행으로 유지한다.

현재 기록이 이미 공유 원본인 경우에는 앱에서 다시 `로컬 기록 합치기`를 실행하지 않는다. 초대받아 참여하는 사람의 로컬 기록도 자동 업로드하지 않는다.

## 9. 구현·검증 순서

1. **격리 DB의 장부 관리 기반:** 목록·생성·저장 경로 매핑·초대·수락·권한·나가기 구현. 실제 이메일 발송과 운영 초대는 하지 않는다.
2. **새 장부 금융 저장 경로:** 모든 테이블과 API를 장부 범위로 구현. 동일한 행 ID를 가진 두 장부로 교차 접근·수정·삭제·cursor·operation·참조 검증.
3. **기존 장부 adapter:** 기존 웹 핸들러를 유지하고 인증 API와 연결. 테스트 DB에서 양쪽 경로의 기록·revision·재시도·409·증분 결과 비교.
4. **앱 UI와 초대 수락:** 최소한의 관리 화면, 서로 다른 두 Google 계정, 잘못된 계정·만료·취소·동시 수락·viewer 쓰기·권한 철회·보류 변경 확인.
5. **운영에 첫 장부 등록·새 API 추가:** 원본 백업과 현재 스키마를 확인한 뒤 추가 메타데이터·새 테이블만 배포. 현재 기록의 건수·참조·조회 결과가 동일하고 이전 웹에서 등록·수정·삭제·정기·카드 결제·복원이 동작하는지 확인. 새 원격 요청을 차단하는 롤백 경로를 준비하며 기존 금융 원본은 되돌리지 않는다.
6. **웹 기능 반영:** 별도 검증 페이지에서 Google 로그인·장부 선택·초대를 확인. 여자친구의 초대 수락과 동일한 첫 장부 접근을 확인한 뒤 현재 웹의 인증 API 전환을 배포한다. 익명 경로 종료는 이 시점의 명시적인 전환 작업으로 처리한다.

완료 기준은 앱과 웹이 같은 첫 장부 UUID·원본을 사용하고, 새 장부가 이전 웹 응답에 섞이지 않으며, 계정·장부 간 접근과 쓰기가 차단되고, 초대 수락이 중복·잘못된 계정·만료를 안전하게 처리하는 것이다. 운영 장부에 시험 금융 행을 생성하거나 전체 snapshot POST로 검증하지 않는다.
