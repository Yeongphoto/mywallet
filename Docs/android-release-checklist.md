# Memoney / 메머니 Android 출시 준비

작성: 2026-10-23 · 작업 브랜치: `android_dev`

## 확정 사항과 작업 범위

- 사용자 확정 앱명: 영문 `Memoney`, 한국어 `메머니`. 2026-10-23 사용자 정정에 따라 영문은 대소문자까지 이 표기로 통일한다.
- 지금 목표는 출시 준비와 단계별 검증이다. 공개 출시, 원격 푸시, 운영 배포, DB 변경·삭제를 이 문서 작성으로 승인받은 것으로 보지 않는다.
- 각 단계는 변경 범위 확인 → 구현 또는 콘솔 준비 → 검증 → 로컬 커밋 → 결과 기록 순서로 진행한다.
- 기존 개발 앱, Google 계정과 장부 UUID, 공통 인증·개인·공유 DB, 저장 키를 보존한다. 표시 이름 변경을 데이터 이전이나 내부 식별자 일괄 치환으로 처리하지 않는다.
- 기존 개발·동기화 규칙과 [최초 개인 장부 이전 계약](personal-onboarding-contract.md)을 유지한다. 미활성 기능을 출시 준비와 함께 임의 활성화하지 않는다.

## 1단계: 현황 조사와 출시 기준 정리 — 완료

2026-10-23 확인한 상태:

| 항목 | 현재 상태 | 후속 처리 |
| --- | --- | --- |
| Play Console | 개인 계정, 홈에 첫 앱 만들기 표시 | 계정 인증 상태 확인 후 앱 초안 준비 |
| 표시 이름 | Capacitor `Memoney Dev` | 출시용 `Memoney` / `메머니`, 개발용 구분 유지 |
| Android 식별자 | `com.mywallet.dev` | 기존 유지, 출시용 식별자는 최초 AAB 업로드 전 확정 |
| 버전 | versionCode 9, versionName 0.3.4 | 개발/출시 채널별 증가 규칙 정리 |
| SDK | min 24, compile/target 36 | 실제 업로드 시 Play 요구사항 재확인 |
| Release | Gradle taskGraph에서 차단 | 보안·인증·서명·서버 구성이 검증되기 전 해제 금지 |
| 서버 주소 | `https://memoney-android-test.pages.dev/signin` | 출시용 HTTPS origin과 API 구성을 별도 확정 |
| Google 로그인 | 기존 Web/Android 개발용 OAuth client 설정 | 출시 패키지와 Play 앱 서명 인증서에 맞는 client 추가 |
| 서명 | app/build.gradle에 출시 signingConfig 없음 | 업로드 키 생성·비밀 보관·복구 절차 준비 |

위 코드 값은 `capacitor.config.json`, `android/app/build.gradle`, `android/variables.gradle`에서 확인했다. 콘솔 홈만으로 본인·연락처·기기 인증이 모두 완료됐다고 판단하지 않는다. Google OAuth Audience의 현재 상태는 별도 콘솔 확인이 필요하며, 과거 문서의 Testing 기록을 최신 확인으로 보지 않는다.

## 2단계: 출시용 식별자와 설정 검사 — 기반 구현 완료, 빌드 분리는 미완료

- [x] 사용자 위임에 따라 출시 패키지명은 `com.memoney.app`으로 선정했다. 실제 Play 업로드는 아직 하지 않았다. 이 ID가 별도의 `memoney.com` 도메인 소유를 증명하는 것은 아니다.
- [x] 기존 개발 소스는 유지하고 출시 준비용 프로젝트를 별도 생성 폴더에 만드는 경로를 구현했다. 실제 배포 AAB 빌드 경로는 아직 잠겨 있다.
- [x] 출시 프로필 `config/android-release.json`에 기본 이름 `Memoney`, 한국어 이름 `메머니`를 기록했다. 실제 Android 리소스와 Play 현지화 반영은 빌드 분리 때 처리한다.
- [x] 개발 앱 식별자·서버·OAuth·리소스 검사를 sync 전과 build/run 진입에 추가했다. 출시 프로필은 별도 검사 명령만 제공하며 현재 활성 개발 설정을 덮어쓰지 않는다.
- [x] [출시 서버·로그인·로컬 보존 준비](android-release-server.md)에 변경 목록과 격리 검사 결과를 기록했다. 번들/API 호환 구현·Google 콘솔 등록·실기기 검증은 아직 남아 있다.
- [ ] 개발 설정 불변 검사는 구현했다. 설치 앱의 실기기 업데이트·로컬 데이터 접근 회귀 검증은 실제 출시 빌드 구성 후 수행한다. 서로 다른 패키지/origin의 로컬 기록이 자동 공유된다고 가정하지 않는다.

완료 기준: 개발 앱을 깨뜨리지 않는 출시 구성안과 실제 변경 목록이 있고, 불변 식별자와 서버 주소가 확정돼 있다. 이 단계가 끝나기 전 서명된 출시 AAB를 업로드하지 않는다.

### 2026-10-23 주소 확보와 검사 도구

- Cloudflare Pages에 빈 프로젝트 `memoney`를 생성했다. 실제 할당 주소는 `https://memoney-6r5.pages.dev`, production branch는 `android_dev`이다. 원하는 `memoney.pages.dev`와 `memoney-app.pages.dev`는 이미 다른 사이트가 사용 중이다.
- 이 프로젝트는 배포 0건이며 아직 서비스 URL이 아니다. DB 바인딩·환경변수·OAuth origin·배포를 설정하지 않았다. `test` 없는 주소 확보와 서비스 이전 완료를 구분한다.
- 기존 `memoney-android-test` 프로젝트, 설치 앱의 origin, 데이터 저장 키, DB, OAuth client, 네이티브 식별자는 그대로 유지했다.
- `npm run check:android-dev`: 기존 개발 앱 설정 일치 확인. `npm run android:sync`가 변경 작업 전에 이 검사를 실행한다.
- `npm run check:android-config`: 격리된 메모리 설정으로 혼합·오타·디버그 인증서 재사용 차단을 검증한다.
- `npm run android:release:check`: 출시 프로필의 미완료 값을 보고하고 실패한다. Android OAuth client, Play 앱 서명 SHA-1, 업로드 키, 서버 배포 확인, origin 이전 검증의 5개 항목이 현재 미완료다. 값을 채웠다는 사실만으로 보안 감사나 출시 승인이 완료되는 것은 아니다.
- Gradle의 기존 Release 차단은 유지한다. 별도 네이티브 준비 경로와 기본/한국어 리소스 분리는 [출시 네이티브 준비](android-release-build.md)에 구현·정리했다. 준비 프로젝트의 APK/AAB 생성·설치는 차단하며 실제 서명 빌드는 아직 추가하지 않았다.
- 현재 앱의 원격 `server.url` 구조는 개발 설정이다. [Capacitor 설정 문서](https://capacitorjs.com/docs/config)는 이를 실시간 개발 용도로 안내하므로, 출시 전 번들 자산 + 원격 API 방식과 현재 네이티브 로그인/로컬 저장 경로의 호환성을 검토한다. 새 URL을 그대로 끼워 넣는 것만으로 출시 설계를 완료하지 않는다.

## 3단계: Play Console 초안과 계정 준비

- [ ] 계정 관리에서 본인·연락처·Android 기기 인증의 미완료 안내를 확인한다. 사용자 본인 확인은 사용자가 수행한다.
- [ ] 기본 언어 한국어, 이름 `메머니`로 앱 초안을 준비하고 영문 현지화 이름 `Memoney`를 정리한다.
- [ ] 앱/게임 구분은 앱. 무료/유료, 광고 여부, 대상 연령, 출시 지역, 지원 이메일은 실제 운영 방침에 맞게 확정한다. 미정 항목을 임의 신고하지 않는다.
- [ ] 약관·법적 선언·콘솔 저장은 입력 내용을 사용자에게 제시한 뒤 명시적인 실행 요청 범위에서 처리한다. 앱 생성과 공개 출시는 별개다.

## 4단계: 서명과 Google 로그인

- [ ] Play App Signing 구성과 별도의 업로드 키를 준비한다. 키·비밀번호·서비스 계정 JSON은 Git, 채팅, APK에 넣지 않는다.
- [ ] 키의 안전한 별도 백업과 담당자·복구 절차를 기록한다. 공개 인증서 지문만 문서에 기록한다.
- [ ] 출시 패키지 + Play 앱 서명 SHA-1로 같은 Google Cloud 프로젝트에 Android OAuth client를 준비한다. 업로드 키 SHA-1과 혼동하지 않는다.
- [ ] 서버의 Web client audience와 Android authorized-party 허용 목록, 브라우저 origin을 맞춘다. 기존 개발 client를 지우거나 임의 교체하지 않는다.
- [ ] OAuth Audience, 동의 화면 이름·도메인·정책 링크·요청 scope를 점검하고 필요한 공개 전환/검증 여부를 확인한다.
- [ ] Play에서 설치한 앱으로 Google 로그인·취소·로그아웃·재로그인·앱 재시작을 검증한다.

## 5단계: 사용자 데이터와 운영 준비

- [ ] 개인정보처리방침 URL, 지원 연락처, 데이터 내보내기와 계정 삭제 경로를 준비한다.
- [ ] 앱 내부와 외부 웹에서 계정 및 관련 데이터 삭제를 요청할 수 있게 한다. 장부 초기화·7일 복구를 탈퇴로 대체하지 않는다.
- [ ] 탈퇴 시 공유 장부 소유권·다른 구성원의 기록·백업 보존 처리는 정책을 먼저 확정한다. 정상 데이터를 임의 삭제하지 않는다.
- [ ] 실제 수집 항목·SDK·전송·보관·삭제를 조사한 뒤 데이터 보안, 콘텐츠 등급, 금융 기능 등 콘솔의 해당 신고를 작성한다.
- [ ] 비로그인 기기별 로컬 보존, 최초 로그인 1회 이전, 기존 개인 장부 우선, 앱/웹 동기화, 타인 접근 차단, 초대 권한과 7일 복구를 분리된 시험 장부로 검증한다.
- [ ] 최초 이전 기능의 인증 스키마/동시 활성화는 별도 승인과 배포 절차로 다룬다. 현재 플래그를 임의로 켜지 않는다.
- [ ] 의존성·권한·릴리스 로그·백업 설정·WebView 보안·장애 복구를 점검한다. 기존 실데이터를 수정·삭제하는 검증은 금지한다.

## 6단계: 내부 테스트용 AAB

- [ ] 앞 단계의 안전 조건을 충족한 뒤 Release 차단을 필요한 범위에서 변경한다.
- [ ] 서명된 AAB와 버전 증가 규칙을 검증하고 Play 내부 테스트에 업로드한다. 개발 APK 배포와 혼동하지 않는다.
- [ ] 설치·업데이트, 오프라인·네트워크 복귀, 뒤로가기·키보드·파일/첨부·로고/스플래시를 실기기에서 확인한다.
- [ ] Play 심사용 로그인/접근 방법을 준비하되 개인 계정 자격증명과 실장부는 제공하지 않는다.

## 7단계: 비공개 테스트 → 공개 출시 판단

- [ ] 새 개인 계정의 현재 요건인 최소 12명, 연속 14일 참여 비공개 테스트를 계획한다. 내부 테스트 기간을 이 요건으로 계산하지 않는다.
- [ ] 실제 사용 시나리오와 피드백·오류 수정 기록을 남긴 뒤 프로덕션 액세스를 신청한다. 기간 충족만으로 승인이 자동 보장되는 것은 아니다.
- [ ] 아이콘·스크린샷·소개·현지화·정책 신고를 최종 검수한다.
- [ ] 공개 출시와 공개 범위는 사용자의 최종 요청 후 진행한다.

## 공식 기준과 관련 문서

- [앱 생성·패키지명·AAB](https://support.google.com/googleplay/android-developer/answer/9859152?hl=en): 패키지명은 고유하고 영구적이다.
- [새 개인 계정 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en): 최소 12명, 연속 14일 비공개 테스트 후 프로덕션 액세스 신청.
- [Android OAuth 인증서](https://developers.google.com/android/guides/client-auth): Google 로그인 SHA-1 및 Play 앱 서명/업로드 키 구분.
- [앱 계정 삭제 요건](https://support.google.com/googleplay/android-developer/answer/13327111?hl=ko): 인앱 삭제 경로와 외부 웹 요청 경로.
- [기존 Google Cloud 구성](google-cloud-setup.md), [Android 이식 기록](android-port-plan.md), [공개형 앱 설계](public-app-auth-plan.md).

과거 문서는 당시 작업 기록으로 보존한다. 이 체크리스트의 새 표시 이름만으로 기존 OAuth·패키지·DB 설정을 일괄 변경하지 않는다. Google 정책은 실제 업로드·출시 시점에 다시 확인한다.
