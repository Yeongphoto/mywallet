# MyWallet 공개형 앱 전환 계획

> 상태: 구현 전 계획안 · 작성: 2026-10-01
> 범위: 웹/PWA의 공개 가입과 사용자별 장부 분리, 이후 모바일 앱 배포를 위한 기반. 이 문서는 구현 승인이나 원격 D1 변경 승인이 아니다.

## 목표와 원칙

- 누구나 자신의 계정을 만들 수 있고, 로그인한 사용자만 본인 장부를 읽고 변경한다. 새 계정은 거래·자산·계획이 없는 상태로 시작한다.
- 현재 단일 사용자 장부는 지정된 기존 소유자 계정으로만 이전한다. 다른 신규 계정에 복사하거나 브라우저 캐시만으로 소유자를 추정하지 않는다.
- Cloudflare D1을 기준 저장소로 유지한다. 로그인은 데이터 접근 자격을 결정하고, `user_id`는 서버가 검증한 신원에서만 얻는다.
- 기존 데이터와 동기화 안정성을 보존하면서 단계적으로 전환한다. 공개 가입은 사용자 간 격리 시험을 통과한 뒤에만 연다.
- 이 문서는 [다중 사용자 데이터 설계 메모](multi-user-data-plan.md)를 실행 순서로 구체화한 것이다. 저장 정책은 [동기화 규칙](sync-rules.md)과 [개발 규칙](development-rules.md)이 우선한다.

## 현재 상태와 공개 전 차단 사유

- `functions/api/data.ts`의 GET·PATCH는 계정 확인 없이 D1에 접근한다. 전체 조회, `?after=` 변경 내역, 거래·자산·설정 등의 작업 모두 사용자별 권한 경계가 없다. 현재 배포가 외부에서 별도로 보호되는지는 코드만으로 확인되지 않는다.
- `schema.sql` 및 `migrations/0001`~`0007`의 주요 테이블에는 소유자 열이 없다. `settings.key`, `plans(category, type)`, `custom_categories(id, type)`, `operation_results.operation_id`, `sync_groups.id` 등의 고유 키도 단일 장부를 전제한다.
- `src/App.tsx`, `src/d1-cache-preload.ts`는 `mywallet:v2`, 보류 작업, 동기화 커서 등을 계정 구분 없이 같은 브라우저 저장소에 둔다. 로그인만 추가하면 계정 전환 시 이전 사용자의 캐시가 보이거나 업로드될 수 있다.
- `public/sw.js`는 현재 `/api/` 요청을 네트워크 전용으로 처리한다. 이 동작은 유지하되, 로그인 뒤의 앱 화면과 로그아웃 이후 캐시 노출도 별도로 시험한다.
- 따라서 현재 API를 그대로 공개형 서비스에 노출하지 않는다. 기존 개인용 배포의 접근 보호 상태를 먼저 확인한다.

## 제안 아키텍처

1. **신원 확인:** 비밀번호 저장을 직접 구현하지 않고, 공개 가입을 지원하는 관리형 OpenID Connect(OIDC) 제공자를 선택한다. 첫 출시의 로그인 수단과 계정 복구·탈퇴 지원 여부는 별도 결정한다. 이메일 주소는 변경될 수 있으므로 장부 소유 키로 쓰지 않는다.
2. **앱 사용자:** D1에 `users(id, created_at, status, ...)`와 `auth_identities(user_id, issuer, subject, ...)`를 둔다. 외부 제공자의 `(issuer, subject)`를 내부의 불변 `users.id`에 매핑한다. 동일 이메일의 계정을 자동 병합하지 않는다.
3. **웹 세션:** Pages Functions가 로그인 콜백을 검증하고 앱 세션을 발급한다. 브라우저에는 `Secure`, `HttpOnly`, 적절한 `SameSite`를 가진 `__Host-` 세션 쿠키만 둔다. 인증 토큰·세션 ID를 `localStorage`에 저장하지 않는다. 로그아웃·만료·철회와 계정 전환을 명시적으로 처리한다. 쿠키 기반 변경 요청에는 `Origin` 검사와 CSRF 방어를 설계한다. [OWASP 세션 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
4. **인증 플로우:** OAuth/OIDC 사용 시 Authorization Code + PKCE, `state`/`nonce`, 정확한 리다이렉트 URI 검증을 적용한다. 이후 네이티브 앱은 시스템 브라우저 기반 로그인과 플랫폼에 맞는 안전한 세션 보관을 별도로 설계한다. [OAuth 보안 권고 RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).
5. **서버 권한 경계:** `functions/api`의 공통 인증 미들웨어에서 세션을 검증하고, 각 핸들러는 검증된 `user_id`를 받는다. Pages Functions는 경로별 미들웨어를 지원하지만, 미들웨어 통과만으로 끝내지 않고 모든 SQL 조회·수정·삭제에 소유자 조건을 적용한다. 요청 본문의 `user_id`, 임의 이메일, 클라이언트가 지정한 대상 계정은 신뢰하지 않는다. [Cloudflare Pages Functions 미들웨어](https://developers.cloudflare.com/pages/functions/middleware/).
6. **데이터 저장:** 초기에는 하나의 D1에서 모든 장부 테이블을 `user_id`로 분리한다. 작은 사용자 수에는 운영이 단순하지만 격리는 애플리케이션의 모든 쿼리가 강제해야 한다. D1의 사용자별 DB 분리도 향후 선택지로 남기며, 실제 규모와 제한을 재평가한다. [Cloudflare D1 제한](https://developers.cloudflare.com/d1/platform/limits/).

## 데이터·동기화 전환 범위

- 소유자 추가 대상: `transactions`, `assets`, `plans`, `custom_categories`, `settings`, `recurring_rules`, `deleted_recurring_txs`, `card_settlements`, `operation_results`, `sync_changes`, `sync_groups`. 새 테이블과 후속 기능에도 같은 규칙을 적용한다.
- 사용자 범위 고유 키와 인덱스를 재설계한다. 예를 들어 설정은 `(user_id, key)`, 계획은 `(user_id, category, type)`, 작업 중복 방지는 `(user_id, operation_id)`로 범위를 한정한다. 전역 UUID를 유지하더라도 조회·업데이트·삭제 조건은 항상 소유자를 함께 검사한다.
- 거래가 참조하는 자산·카드 결제·정기 규칙·이체 상대 자산이 **같은 사용자** 소유인지 서버에서 검증한다. ID만 알고 다른 사용자의 레코드를 연결하거나 덮어쓸 수 없어야 한다.
- 전체 데이터 조회와 `sync_changes` 증분 조회 모두 서버 검증 `user_id`로 제한한다. 변경 payload, 삭제 이력, 정기 자동생성, 카드 결제, `sync_groups`의 revision 및 커서가 다른 사용자에게 섞이지 않도록 한다. 현재 전역 커서를 사용자별로 필터링해 쓸지, 사용자별/불투명 커서로 바꿀지는 동기화 시험 뒤 결정한다.
- 브라우저의 장부 캐시·백업·보류 작업·동기화 커서는 계정별 네임스페이스로 분리한다. 로그아웃 시 화면의 이전 데이터를 즉시 숨기되 미전송 작업을 무조건 삭제하지 않는다. 다른 계정의 보류 작업을 새 계정에 자동 업로드하지 않는다. 인증 전의 기존 `mywallet:v2`는 안전한 이전 확인 전까지 격리한다.
- D1 우선 정책과 `pendingSyncAt`의 의미는 유지한다. 인증 실패·세션 만료·네트워크 실패·중복 제출을 구별하여 재시도하고, 오래된 로컬 캐시가 원격 데이터를 덮어쓰지 않도록 한다.

## 단계별 작업과 완료 기준

### 0. 결정·백업·시험 환경

- 공개 가입 범위, 첫 로그인 수단/제공자, 기존 장부를 받을 계정, 탈퇴·내보내기 정책을 결정한다.
- 현재 원격 D1 및 배포 접근 경로를 확인하고, 백업과 복원 연습을 마친다. 개발·스테이징·운영 D1을 분리한다. `schema.sql`에는 `DROP TABLE`이 있으므로 운영 DB에 재실행하지 않고 추가 마이그레이션만 사용한다. [Cloudflare D1 마이그레이션](https://developers.cloudflare.com/d1/reference/migrations/), [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/).
- 완료 기준: 원격 원본의 테이블별 건수·관계·복구 지점 기록, 스테이징 복원 성공, 전환·중단 절차 문서화.

### 1. 인증 골격과 비공개 시험

- 가입/로그인/로그아웃/세션 확인 API, 공통 인증 미들웨어, 내부 사용자 매핑을 만든다. `/api/data`는 미인증 시 본문 데이터 없이 401을 반환하도록 한다.
- 관리자/기존 소유자만 들어오는 비공개 환경에서 먼저 시험한다. Cloudflare Access는 비공개 베타의 추가 입구 보호 수단일 수 있지만, 공개 앱의 사용자별 D1 소유권 검사를 대신하지 않는다. [Access 정책](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/).
- 완료 기준: 로그인 실패·만료·로그아웃 후 모든 장부 API 거부, 다른 계정으로 바뀌면 이전 화면이 보이지 않음.

### 2. D1 소유권 마이그레이션과 API 전수 수정

- 운영 원본 백업 후 스테이징에서 사용자 열·인덱스·고유 키를 점진적으로 추가한다. 기존 모든 행의 소유자를 **사용자가 지정한 계정**으로 채운다. 소유자가 없는 행을 어느 계정에도 노출하지 않는다.
- `functions/api/data.ts`의 GET/PATCH 전 작업과 추가 API를 소유자 범위로 수정한다. 읽기뿐 아니라 생성 시 참조 검증, 수정/삭제의 조건부 WHERE, 중복 작업 결과, 정렬/계획/설정 일괄 변경까지 포함한다.
- 완료 기준: 새 계정은 빈 장부, 기존 계정은 이전 전과 동일한 수치·정기기록·카드 결제 이력, 사용자 A가 B의 ID나 operation ID를 알아도 조회·수정·삭제 불가.

### 3. 계정별 클라이언트 상태와 동기화

- 앱 시작 순서를 `세션 확인 → 계정 식별 → 해당 계정 캐시 확인 → 해당 계정 D1 동기화`로 바꾼다. 로그인 전에는 D1 캐시 선적재와 원격 저장을 시작하지 않는다.
- 계정 전환, 오프라인 보류 작업, 중복 탭, 로그아웃 중 미전송 작업, 로그인 후 오래된 캐시 복원, 삭제 tombstone과 정기 자동생성을 검증한다.
- 완료 기준: 같은 기기에서 A→로그아웃→B→A를 반복해도 화면·캐시·서버 데이터가 섞이지 않고, 실패한 저장은 원래 소유자 계정에서만 재시도됨.

### 4. 공개 베타와 배포 준비

- 초대형 베타에서 두 개 이상 실제 시험 계정으로 교차 접근 시험을 수행한다. 인증·권한 실패율, D1 읽기/쓰기 비용, 동기화 충돌, 백업·복원, 세션 만료를 관찰한다. 오류 로그에는 거래 제목·금액·세션 비밀을 남기지 않는다.
- 공개 가입 전에 남용 방지(가입/로그인 요청 제한, 봇 방어), 개인정보 처리·내보내기·탈퇴, 지원·장애 대응 문서를 마련한다. 개인정보·앱스토어 요구 사항은 출시 시점과 배포 지역에 맞춰 별도 검토한다.
- 웹/PWA 공개가 안정화된 뒤 Android/iOS 패키징, 시스템 브라우저 로그인 복귀, 푸시/딥링크 및 스토어 심사를 별도 단계로 진행한다. 네이티브 앱을 만들더라도 동일한 서버 소유권 검사를 우회하지 않는다.
- 완료 기준: 아래 필수 시험 통과, 복원 절차 확인, 비공개 보호에서 공개 가입으로 바꾸는 명시적 승인.

## 필수 격리·복구 시험

1. 미로그인 GET, 변경 요청, 증분 동기화는 데이터 없이 401. 로그인 사용자는 다른 사용자의 거래·자산·정기 규칙 ID를 넣어도 접근할 수 없음.
2. 같은 `operation_id`, 카테고리 이름, 설정 키를 두 계정이 사용해도 서로의 결과·값이 보이지 않음. 변경 커서와 삭제 이벤트도 섞이지 않음.
3. 새 사용자 가입 직후 빈 장부와 기본 카테고리만 보임. 기존 사용자의 장부는 지정된 계정에서만 이전 전후 건수·합계가 일치함.
4. 다른 사용자 자산을 참조하는 거래·카드 결제·이체 요청은 거부되고, 부분 저장이 남지 않음.
5. A의 오프라인 보류 작업이 B 로그인 중 전송되지 않음. 세션 만료 후 재로그인과 중복 제출에도 거래가 중복 생성되지 않음.
6. 스테이징에서 운영 백업 복원, 마이그레이션 실패 중단, 코드 롤백 시 데이터 비노출을 연습함.

## 구현 전에 사용자와 결정할 사항

- 첫 가입 방식: Google 등 소셜 로그인, 이메일 링크, 또는 둘 다. 제공자는 OIDC 지원, 비용, 계정 복구·탈퇴, 운영 부담을 비교해 선정한다.
- 기존 D1 장부를 받을 최초 계정과 공개 전환 시점. 현재 데이터는 **자동으로 첫 가입자에게 귀속하지 않는다**.
- 베타를 초대제로 시작할 기간과 공개 가입을 여는 조건.
- 내보내기 형식, 계정 삭제 시 유예/보존 기간, 백업 접근자, 고객 문의 채널.

이 결정이 끝나기 전에는 운영 D1 스키마 변경, 기존 데이터 귀속, 로그인 제공자 계약·설정, 공개 배포를 실행하지 않는다.
