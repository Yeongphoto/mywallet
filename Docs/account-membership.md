# 계정별 관리자·테스터 프리미엄

사용자 요청: 내부 테스터에게 프리미엄을 제공하고 공개 출시 후에도 목록을 유지한다. 슈퍼 계정은 설정의 계정 관리에서 기존 Google 로그인 이메일로 테스터를 추가·해제할 수 있다. Google Play 테스터 설치 자격과 메머니 혜택 목록은 별개이며 APK 설치 여부로 프리미엄을 판정하지 않는다.

초기 확인 계정은 `syh4472@gmail.com`(슈퍼 관리자), `mangaji93@gmail.com`(내부 테스터)다. 공통 인증 DB `ec28198a-6040-4074-a142-1cf6f76c7f15`의 `auth_identity_profiles`에서 두 이메일의 권위 있는 Google 프로필을 읽기 전용으로 확인했다. 읽은 행은 2건, 쓴 행은 0건이다. 실제 혜택 연결에는 이메일이 아닌 기존 고정 user UUID를 사용한다. 새 사용자·새 장부·새 Google 연결을 만들지 않는다.

슈퍼 관리자 UUID는 서버 전용 `server/billing/account-benefits.ts`에서 보호한다. 사용자/테스터가 요청 본문·로컬 저장소·앱 버전으로 관리자 자격을 만들 수 없다. 슈퍼 자격도 다른 사용자의 개인·공유 장부에 대한 접근 권한을 부여하지 않는다. UI의 계정 관리에서는 슈퍼 자격 변경을 지원하지 않는다.

테스터는 인증 DB의 `account_premium_grants`로 관리하며 `account_premium_audit`에 부여·해제 이력을 남긴다. 한 batch에서 목록과 이력을 같이 저장한다. 해제도 행을 지우지 않고 active=0으로 보존한다. 초기 스키마를 다시 적용해도 해제한 계정이 부활하지 않는다. 금융 백업/복구·장부 초기화·공유 해제·앱 업데이트·공개 트랙 전환에 이 목록을 복사하거나 초기화하지 않는다. 기한 없는 테스터 혜택이며 관리자가 해제할 수 있다. 일반 유료 연 구독은 기존 구매 검증/만료 규칙을 따른다. 테스터 혜택 해제로 이미 구입한 유료 구독까지 취소하지 않는다.

`GET /api/account/membership`은 현재 세션의 `free / premium_yearly / premium_tester / premium_admin`을 반환한다. 계정 영역에서 일반/프리미엄/내부 테스터/슈퍼 관리자를 구분한다. `GET/POST /api/account/manage`는 서버에서 슈퍼 계정만 허용하고 POST origin·본문 필드·크기·대상 계정을 검사한다. 등록 대상은 앱에 로그인해 권위 있는 Google 이메일 프로필이 있는 활성 계정이다. 같은 이메일이 여러 사용자에 대응하면 임의 선택하지 않고 거절한다. 직접 URL/API 접근도 일반 회원과 테스터에게는 403이다.

혜택 정책의 `monetizationPolicyForAccounts`는 현재 DB 자격(해제 포함)을 읽어 판정한다. 호스트 혜택은 공유 장부 자산 한도, 실제 작성자 혜택은 본인 입력 한도·광고에 적용하는 기존 구분을 유지한다. 현재 광고·입력량 차감·결제의 운영 활성화는 별개로 비활성 상태이며 이번 작업으로 켜지 않는다. 테스터/관리자에게 유료 연 구독 시작 화면을 제안하지 않는다.

## 활성화와 배포

구현 커밋 `80486a9` 이후 사용자가 배포를 요청해 아래 순서로 인증 DB 스키마와 서버, 내부 테스트 앱에 적용했다. 후속 배포에서도 공통 DB와 회원 목록을 보존한다.

1. 공통 인증 DB ID와 두 사용자 UUID를 재확인하고 인증 DB를 비공개 위치에 백업한다. 금융 DB는 변경하지 않는다.
2. 해당 인증 DB에 `scripts/account-membership-schema.sql`을 적용한다. 기존 사용자 행을 그대로 참조해 mangaji93 테스터를 최초 등록한다. 슈퍼 계정은 기존 UUID를 유지한다. 스키마가 부분 적용되어도 플래그는 켜지 말고 동일 스크립트의 안전한 재적용으로 완료한다.
3. 목록/초기 행을 확인한 뒤 공통 API 배포에 `ACCOUNT_MANAGEMENT_ENABLED=true`를 설정한다. 꺼져 있으면 DB 테스터 혜택·관리는 비활성이며 임시 클라이언트 자격으로 대체하지 않는다. 공개 출시 후에도 이 플래그와 동일 인증 DB/사용자 UUID를 유지한다.
4. 새 account API 경로와 `/account-management`를 허용한 네이티브 전송 코드가 포함된 앱을 배포한다. 기존 API origin·Google OAuth·서명키·금융 DB는 유지한다.
5. 슈퍼/테스터/일반 세션의 표시·관리 권한을 확인한다. 실사용 장부 변경으로 테스트하지 않는다. 후속 테스터는 슈퍼 계정의 설정 → 계정 관리에서 Google 이메일을 입력해 추가한다.

APK/AAB는 만들지 않았다. Orca에는 실제 계정을 수정하지 않는 로컬 모의 관리 화면을 열어 검수했다.
