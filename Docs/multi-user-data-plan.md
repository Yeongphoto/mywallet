# 다중 사용자 데이터 설계 메모

> 향후 다중 사용자 지원을 위한 검토안이다. 현재 구현된 로그인·사용자 분리 기능이나 확정된 데이터 정책이 아니다. 실제 작업 전에는 `Docs/development-rules.md`와 `Docs/sync-rules.md`를 다시 확인하고, 기존 D1 데이터의 귀속·이전 방식을 결정한다.

## 결론

- Cloudflare D1을 바로 교체할 필요는 없다. 초기에는 하나의 D1 안에서 사용자별 데이터를 `user_id`로 구분하는 방식이 단순하다.
- 로그인은 사용자의 신원을 확인하고, 서버는 검증된 신원에서 사용자 ID를 얻는다. 브라우저가 요청 본문에 넣은 `user_id`를 권한 판단에 사용하지 않는다.
- 새 계정은 거래·자산·계획이 없는 상태로 시작한다. 기본 카테고리 등 공통 초기값이 필요하면 계정 생성 시 별도로 설정한다. 다른 사용자의 장부나 현재 단일 사용자 장부를 복제하지 않는다.
- 다시 로그인하면 해당 사용자 ID의 D1 데이터만 읽는다. 원격 D1을 기준 저장소로 삼는 현재 정책은 유지한다.

## 현재 코드에서 확인한 상태

- `functions/api/data.ts`의 GET은 인증된 사용자 확인이나 사용자별 조건 없이 거래, 자산, 계획, 카테고리, 설정, 정기기록, 삭제된 정기 거래, 카드 결제와 동기화 변경 내역을 읽는다. 다른 API 작업도 동일한 관점에서 전수 점검해야 한다.
- `schema.sql`과 후속 마이그레이션의 주요 테이블에는 사용자 소유자가 없다. 특히 `settings.key`, `plans(category, type)`, `custom_categories(id, type)`, `operation_results.operation_id`, `sync_groups.id`와 `sync_changes.cursor`는 현재 전체 장부를 하나로 보는 구조다.
- `src/App.tsx`와 `src/d1-cache-preload.ts`의 `mywallet:v2` 계열 로컬 저장 키, 보류 작업 및 동기화 커서도 사용자별로 분리되어 있지 않다.
- 배포 환경의 외부 접근 제한 여부는 이 코드 조사만으로 확정할 수 없다. API 코드 자체에는 사용자별 권한 검사가 없다.

## 사용자별 데이터 흐름

1. 사용자가 가입하거나 로그인한다. 인증 제공 방식(예: 외부 로그인, 이메일 링크)은 구현 전에 결정한다. 이메일 주소 대신 변경되지 않는 고유 사용자 ID를 데이터 소유 키로 사용한다.
2. 서버가 매 요청에서 세션을 검증하고 사용자 ID를 확인한다. 인증되지 않은 요청은 장부 API에 접근할 수 없도록 한다.
3. 거래·자산·계획·카테고리·설정·정기기록·카드 결제 등 모든 사용자 데이터의 읽기·쓰기·수정·삭제에 소유자 조건을 적용한다. 레코드 ID를 알고 있어도 다른 사용자의 항목은 조작할 수 없어야 한다.
4. `sync_changes` 조회와 동기화 커서는 사용자별로 분리한다. 한 사용자의 변경 내역이나 삭제 기록이 다른 사용자에게 전달되면 안 된다.
5. 브라우저 캐시, 보류 작업, 백업 후보도 계정별로 구분한다. 계정 전환·로그아웃 때 이전 계정의 장부가 화면에 재사용되지 않도록 한다. 다만 미전송 작업은 먼저 안전하게 보존·처리해야 한다.

예시: `transactions`에 `user_id`가 있다면 조회는 `WHERE user_id = ? AND deleted_at IS NULL`처럼 제한한다. 이 `?`에는 서버가 검증한 사용자 ID만 바인딩한다. `settings`처럼 지금은 키가 전역 고유인 테이블은 `(user_id, key)`처럼 사용자 범위의 고유 키로 바꿔야 한다. 자산 ID와 거래의 참조 관계, 정기 생성 ID 및 작업 중복 방지 키도 사용자 경계를 함께 검토한다.

## 기존 장부 이전 시 주의

1. 원격 D1을 백업하고 복원 가능성을 확인한다. `schema.sql`에는 `DROP TABLE`이 있으므로 기존 데이터에 초기 스키마를 재실행하지 않는다.
2. 현재 단일 사용자 데이터를 어느 새 계정에 귀속할지 소유자가 결정한다. 신규 계정에 자동으로 제공하거나 브라우저 캐시를 근거로 귀속하지 않는다.
3. 기존 행의 소유자를 단계적으로 채우는 마이그레이션을 작성하고, 읽기·쓰기 API가 모두 사용자 경계를 강제하도록 전환한다. 중간 단계에서 소유자가 없는 행이 공개되지 않도록 한다.
4. 이전 전후의 테이블별 건수, 연결 관계, 정기기록·삭제 이력·카드 결제, 동기화 재시도와 계정 전환을 검증한다. 기존 D1 데이터를 지우거나 덮어쓰는 복구 경로도 다시 점검한다.

## 선택이 필요한 항목

- 본인·소수 초대 사용자만 쓸지, 누구나 가입하는 공개 앱으로 만들지
- 로그인 방식과 세션 관리 방식
- 기존 장부를 받을 최초 계정과 이전 시점
- 계정 삭제·데이터 내보내기·백업·복구 정책
