# MyWallet 작업 규칙

> 이 문서는 MyWallet 개발에서 가장 높은 우선순위를 가진 작업 규칙이다.  
> 모든 작업은 시작 전에 이 문서를 먼저 읽고 따른다.
>
> 특히 **금융 데이터의 저장·동기화·복구 무결성은 UI, 편의성, 개발 속도보다 항상 우선한다.**
>
> 이 문서와 기존 코드의 동작이 충돌하면 기존 동작을 그대로 유지하지 말고, 먼저 충돌 사실을 확인한 뒤 이 문서의 원칙에 맞게 안전하게 수정한다.

---

# 1. 최우선 불변조건

MyWallet의 장부 데이터는 다음 조건을 항상 만족해야 한다.

## 1.1 데이터 유실 금지

- 서버가 성공 처리한 거래·자산·설정·규칙은 다른 클라이언트의 오래된 상태 때문에 사라질 수 없다.
- 오래된 클라이언트 전체 상태를 서버 정본 위에 덮어쓰는 방식은 어떤 경우에도 허용하지 않는다.
- 저장 성공 여부를 브라우저 상태, localStorage, 로컬 D1 또는 화면 표시만으로 판단하지 않는다.
- 서버의 성공 응답 또는 서버 정본 확인만 저장 성공 근거로 사용한다.

## 1.2 중복 저장 금지

- 동일한 사용자 작업의 네트워크 재시도는 몇 번 발생해도 서버에 한 번만 적용되어야 한다.
- 등록 버튼 중복 클릭, 응답 유실, 네트워크 timeout, 앱 재시작 때문에 거래가 중복 생성되어서는 안 된다.
- 이를 위해 모든 mutation은 안정적인 `operationId`를 사용한다.

## 1.3 무단 덮어쓰기 금지

- 같은 저장 단위가 다른 기기에서 변경되었다면 오래된 값으로 자동 덮어쓰지 않는다.
- 금융 금액, 계좌, 카테고리, 날짜, 거래 종류 등 의미 있는 장부 값은 충돌 시 자동 병합하지 않는다.
- 충돌은 사용자에게 명시적으로 보여 주고 사용자가 다시 저장하도록 한다.

## 1.4 삭제 부활 금지

- 한 기기에서 확정 삭제된 데이터가 오래된 다른 기기의 재접속이나 전체 상태 복구 때문에 다시 생성되어서는 안 된다.
- 삭제 사실은 동기화 계층에서 추적 가능해야 한다.
- 삭제된 데이터의 오래된 수정 요청은 신규 등록로 취급하지 않는다.

## 1.5 최종 수렴 보장

- 네트워크가 정상 상태이고 미해결 사용자 충돌이 없다면 모든 활성 클라이언트는 결국 같은 서버 정본 상태로 수렴해야 한다.
- 다른 기기에서 발생한 변경은 현재 기기에서 별도의 사용자 수정이 없어도 결국 수신되어야 한다.
- 충돌 방지 기능만 구현하고 서버 변경 수신 기능을 생략해서는 안 된다.

# 2. 서버 정본 원칙

## 2.1 서버만 정본이다

- 원격 D1의 서버 상태를 유일한 정본으로 취급한다.
- 브라우저 메모리 상태, React state, localStorage, IndexedDB, `.wrangler`, 로컬 D1은 서버 정본이 아니다.
- 클라이언트 로컬 데이터는 다음 용도로만 사용한다.
  - 화면 표시 캐시
  - pending operation 보존
  - 마지막 sync cursor 보존
  - 네트워크 장애 중 임시 사용자 입력 보존
- 로컬 데이터가 존재한다는 이유로 서버 데이터보다 우선해서는 안 된다.

## 2.2 전체 snapshot 업로드 금지

### 절대 금지

- 일반 사용자 동작에서 전체 데이터 스냅샷을 `POST /api/data`로 저장하지 않는다.
- 서버 테이블을 `DELETE` 후 클라이언트 전체 상태로 재삽입하지 않는다.
- 클라이언트 전체 상태를 서버 정본과 단순 비교한 뒤 서버를 클라이언트에 맞춰 덮어쓰지 않는다.
- 원격 D1의 전역 `updatedAt` 하나로 서로 다른 거래의 최신 여부를 판정하지 않는다.
- 전역 잠금이나 전역 revision으로 독립 거래를 묶지 않는다.

`GET /api/data`는 다음 경우에만 허용한다.

- 최초 로그인
- 신규 기기 bootstrap
- 명시적인 full resync
- sync cursor가 유효하지 않은 복구
- 운영 또는 개발 중 명시적 정본 검증

정상 mutation 이후 전체 `GET /api/data`를 호출해 모든 클라이언트 상태를 교체하는 방식을 기본 저장 흐름으로 사용하지 않는다.

# 3. 세 가지 동기화 식별자의 역할

다음 세 개는 목적이 완전히 다르다.

## 3.1 revision

`revision`은 **현재 클라이언트가 이 저장 단위를 수정할 자격이 있는지 확인하는 값**이다.

- 거래 수정·삭제의 충돌 판정에 사용한다.
- 서버 행의 변경마다 증가한다.
- 다른 행의 revision과 비교하지 않는다.
- 전역 최신성 판정에 사용하지 않는다.
- sync 진행 위치 판단에 사용하지 않는다.

## 3.2 operationId

`operationId`는 **동일한 쓰기 작업을 이미 실행했는지 확인하는 값**이다.

- 네트워크 재시도 멱등성에 사용한다.
- 데이터 최신성 판정에 사용하지 않는다.
- sync 진행 위치 판단에 사용하지 않는다.

## 3.3 sync_seq / sync cursor

`sync_seq`는 **서버 변경의 전달 순서를 나타내는 값**이다.

클라이언트가 마지막으로 정상 적용한 `sync_seq`를 `sync cursor`로 보관한다.

- 다른 기기에서 발생한 변경을 찾아오는 용도다.
- 거래 충돌 판정에는 사용하지 않는다.
- transaction revision을 대신하지 않는다.
- 데이터 의미상의 최신성을 판정하지 않는다.

### 절대 원칙

`revision`, `operationId`, `sync_seq`를 서로 대신 사용하지 않는다.

# 4. 저장 단위와 revision

## 4.1 일반 거래

- 하나의 일반 거래 `transaction.id`가 하나의 저장 단위다.
- 신규 거래 ID는 클라이언트가 안정적으로 생성한다.
- 신규 행의 revision은 서버 저장 성공 시 `1`부터 시작한다.
- 저장 대상 revision은 항상 정수여야 한다.
- migration 완료 이후 revision `NULL`은 허용하지 않는다.

## 4.2 수정

수정 요청은 최소한 다음 정보를 가진다.

- `operationId`
- 대상 `id`
- `expectedRevision`
- 변경값

서버는 다음 조건에서만 수정한다.

`server revision == expectedRevision`

성공하면:

- 변경값 적용
- revision +1
- sync change 기록
- operation 결과 기록

을 같은 원자 작업에서 처리한다.

## 4.3 삭제

삭제도 수정과 동일하게 revision 검사를 한다.

삭제 성공 후 단순히 모든 흔적을 제거해서는 안 된다.

동기화 계층에서 최소한 다음 삭제 정보를 추적할 수 있어야 한다.

- 대상 ID
- 삭제 사실
- 삭제 시점 revision 또는 이에 대응하는 서버 버전
- sync_seq

오래된 클라이언트가 삭제 전 데이터를 가지고 돌아와도 삭제 사실을 알 수 있어야 한다.

## 4.4 이체

- 이체는 하나의 논리 거래 행으로 저장한다.
- 하나의 transaction revision으로 보호한다.
- 이체의 한쪽만 저장되는 부분 성공을 허용하지 않는다.

## 4.5 할부

- 할부 수정은 현재 회차와 남은 회차를 함께 변경할 수 있으므로 `installment_group_id` 단위 그룹 revision을 사용한다.
- 그룹 수정은 하나의 원자 작업으로 실행한다.
- 일부 회차만 변경되고 일부가 실패하는 상태를 허용하지 않는다.

## 4.6 정기기록

- 정기기록 규칙 행은 자체 revision으로 관리한다.
- 규칙 수정·중지·삭제가 이미 생성된 과거 장부 거래를 자동 변경하지 않는다.

## 4.7 자산·카테고리·계획·설정

- 각 저장 단위에 맞는 revision을 사용한다.
- 정렬은 해당 정렬 그룹 revision으로 관리한다.
- 설정은 설정 키별 revision을 사용한다.
- 여러 설정 키를 하나의 전역 저장 revision으로 묶지 않는다.
- 장부 거래와 독립된 데이터 변경이 장부 거래 저장을 막지 않는다.

# 5. operationId 멱등성

모든 mutation은 고유한 `operationId`를 가진다.

## 5.1 같은 작업의 재시도

서버가 동일 operationId를 다시 받으면 mutation을 다시 실행하지 않는다.

기존 저장 결과를 반환한다.

이 규칙은 다음 상황에 모두 적용한다.

- 네트워크 timeout
- 응답 패킷 유실
- 저장 직후 앱 종료
- 브라우저 새로고침
- 재연결 후 자동 재시도

## 5.2 operationId와 payload

operationId는 최초 요청 payload와 결합된 하나의 작업 identity다.

동일 operationId가 다른 대상 또는 다른 mutation payload와 함께 다시 사용되면 정상 재시도로 처리하지 않는다.

반드시 오류로 처리한다.

권장 오류:

`409 OPERATION_ID_REUSED`

서버는 기존 operation의 결과와 충돌 사실을 안전하게 반환할 수 있다.

## 5.3 operation 기록

operation 결과 기록은 적어도 클라이언트가 합리적으로 재시도할 수 있는 기간보다 오래 보존한다.

보존 기간을 줄이거나 cleanup 로직을 추가할 때 멱등성 보장이 깨지지 않는지 먼저 검증한다.

operation 기록을 정리했다는 이유로 오래된 operationId를 신규 mutation처럼 다시 적용해서는 안 된다.

# 6. 서버 원자성

다음 작업은 같은 D1 원자 작업 또는 그와 동등한 트랜잭션 경계 안에서 수행한다.

- 요청 검증
- expected revision 검증
- 데이터 변경
- revision 증가
- sync change 기록
- operationId 결과 기록

중간 단계만 성공하는 상태를 허용하지 않는다.

실패 또는 충돌이면:

- 데이터 변경 없음
- revision 변경 없음
- 잘못된 sync event 생성 없음

을 보장한다.

---

# 7. 서버 변경 로그와 sync

모든 동기화 대상 변경은 서버에서 클라이언트가 추적할 수 있어야 한다.

최소 대상:

- 거래 생성
- 거래 수정
- 거래 삭제
- 이체 변경
- 할부 그룹 변경
- 자산 변경
- 카테고리 변경
- 정렬 변경
- 정기기록 규칙 변경
- 계획 변경
- 설정 변경

각 변경은 증가 방향이 명확한 `sync_seq` 또는 이에 준하는 서버 cursor를 가진다.

## 7.1 incremental sync

클라이언트는 마지막 정상 적용 cursor 이후의 변경을 요청한다.

개념적 요청:

`GET changes after cursor X`

서버는:

- X 이후 변경
- 응답에 포함된 마지막 seq
- 다음 요청에 사용할 cursor

를 반환한다.

## 7.2 cursor 전진

클라이언트는 실제로 적용 완료한 마지막 seq까지만 cursor를 전진시킨다.

서버의 현재 최댓값을 임의로 cursor에 기록하지 않는다.

예:

서버가 `101~120`을 반환했다면 모든 변경이 정상 적용된 후에만 cursor를 `120`으로 저장한다.

동기화 도중 실패하면 이전 안전 cursor에서 다시 요청할 수 있어야 한다.

## 7.3 sync 재적용

동일 change가 네트워크 재시도나 앱 crash 때문에 다시 수신되어도 데이터가 깨지지 않아야 한다.

change 적용은 행 ID, revision, 삭제 상태 등을 이용해 멱등적으로 처리한다.

---

# 8. 삭제 동기화와 tombstone

삭제는 일반 수정과 별도로 특별히 보호한다.

## 8.1 삭제 사실 보존

서버에서 물리 행을 제거하더라도 동기화 계층에는 삭제 사실을 알 수 있는 tombstone 또는 change log가 남아야 한다.

최소 정보:

- entity type
- entity id
- deleted 상태
- 삭제 버전
- sync_seq

## 8.2 삭제 부활 방지

오래된 클라이언트가 삭제된 ID를 수정 요청하면 서버는 이를 신규 생성으로 해석하지 않는다.

삭제 이후 동일 ID를 다시 생성하는 기능이 필요하다면 일반 수정과 명확하게 다른 신규 사용자 행동으로 처리한다.

## 8.3 삭제 정보 보존 기간

삭제 change/tombstone을 정리할 수 있는 경우에도 모든 활성 클라이언트가 해당 삭제를 이미 받았다고 보장할 수 있거나 full resync fallback이 존재해야 한다.

그 보장이 없으면 삭제 기록을 임의로 제거하지 않는다.

---

# 9. 클라이언트 상태 모델

클라이언트에서 다음 세 상태를 구분한다.

## 9.1 server state

마지막으로 서버에서 확인한 정본 표현.

## 9.2 pending operations

아직 서버 성공 확인을 받지 못한 사용자 작업.

pending operation은 서버 정본이 아니다.

그러나 앱 종료, 새로고침, 네트워크 장애로 사용자 작업이 사라지지 않도록 필요하면 영속 저장할 수 있다.

## 9.3 sync cursor

마지막으로 정상 적용 완료한 서버 sync 위치.

### 절대 금지

이 세 상태를 하나의 JSON snapshot으로 합쳐 서버 정본처럼 취급하지 않는다.

---

# 10. pending operation 처리

## 10.1 동일 행

같은 행 또는 그룹에 대한 서버 mutation은 순서대로 전송한다.

서로 다른 행의 작업은 독립적으로 진행할 수 있다.

## 10.2 다른 행 실패 영향 금지

T1 충돌 때문에 독립된 T2, T3 mutation을 중단하지 않는다.

정상 작업은 계속 저장한다.

## 10.3 오프라인 작업

오프라인 또는 timeout 작업은 작업 단위로 pending queue에 보관한다.

재접속 시 원래 operationId로 다시 전송한다.

전체 클라이언트 snapshot을 재전송하는 방식으로 대체하지 않는다.

## 10.4 동일 행의 여러 미전송 수정

같은 행에 서버 전송 전 여러 일반 수정이 누적된 경우 불필요한 중간 mutation을 줄일 수 있다.

단, 압축은 다음 조건에서만 허용한다.

- 모두 아직 서버에서 실행되지 않음이 확실함
- 의미상 하나의 최종 수정으로 안전하게 표현 가능
- operation 경계를 없애도 사용자 의도가 손상되지 않음

등록 → 삭제, 이체, 할부 그룹 작업, 서버 처리 여부가 불명확한 operation은 임의 압축하지 않는다.

서버에서 이미 처리되었을 가능성이 있는 operation은 기존 operationId로 먼저 결과를 확인한다.

---

# 11. pull과 pending operation의 관계

서버 sync 수신과 로컬 pending 작업은 별도로 관리한다.

서버 변경을 받았다는 이유로 pending 사용자 입력을 삭제하지 않는다.

## 11.1 pending이 없는 행

서버 change를 정상 적용한다.

## 11.2 pending이 있는 같은 행

서버에서 더 높은 revision의 변경이 발견되면 로컬 pending 값을 서버 state 위에 자동 덮어쓰지 않는다.

서버 최신 상태를 갱신하고 pending intent는 보존한다.

pending mutation 전송 시 revision 검증을 통해:

- 성공
- 충돌

중 하나로 명확하게 결정한다.

충돌하면 사용자에게 양쪽 값을 보여 준다.

금융 값을 자동 병합하지 않는다.

---

# 12. 신규 기기 bootstrap

신규 기기는 전체 서버 snapshot과 그 snapshot에 대응하는 안전한 sync cursor를 받아야 한다.

중요한 조건:

snapshot과 cursor 사이에 변경 누락 구간이 생겨서는 안 된다.

다음 둘 중 하나가 보장되어야 한다.

- snapshot과 기준 cursor를 서버에서 일관된 시점으로 제공
- snapshot 직후 기준 cursor 이후 incremental sync를 수행해 사이 변경을 반드시 회수

신규 기기는 임의 localStorage 또는 다른 기기의 snapshot을 정본으로 사용하지 않는다.

---

# 13. full resync

incremental sync를 신뢰할 수 없는 경우 명시적인 full resync를 수행할 수 있다.

예:

- cursor 손상
- cursor 보존 범위 초과
- change log retention 초과
- 클라이언트 캐시 손상
- 데이터 구조 migration 후 복구 필요
- 명시적 사용자 복구

## 13.1 full resync 순서

1. 현재 pending operation을 안전하게 보존한다.
2. 서버 정본 snapshot을 받는다.
3. 안전한 sync cursor를 설정한다.
4. server state를 서버 snapshot으로 재구성한다.
5. pending operation을 삭제하지 않는다.
6. 각 pending operation을 최신 서버 상태에 대해 다시 검증한다.
7. 기존 operationId를 유지한 채 정상 재시도 또는 충돌 처리한다.

full resync를 한다는 이유로 pending 사용자 작업을 서버에 무조건 적용하지 않는다.

---

# 14. 충돌 처리

충돌 시 서버는 최소한 다음을 알려야 한다.

- 대상 ID
- 요청 expected revision
- 현재 server revision
- 서버 최신 정본
- 오류 종류

클라이언트는 사용자의 입력을 유지한다.

충돌 화면은 다음을 명확하게 보여 준다.

- 서버 최신 상태
- 사용자가 저장하려던 값
- 무엇이 충돌했는지
- 다시 저장하려면 무엇을 해야 하는지

자동 해결하지 않는 대상:

- 금액
- 계좌
- 카테고리
- 거래 종류
- 날짜
- 자산 값
- 중요한 메모 또는 사용자 의미가 달라질 수 있는 필드

---

# 15. 오류 의미

서버 API 오류 의미를 일관되게 사용한다.

## 400 BAD_REQUEST

요청 형식 또는 필수 필드 문제.

## 404 NOT_FOUND

실제로 존재하지 않는 대상이며 삭제 tombstone 또는 충돌 의미가 아닌 경우.

## 409 REVISION_CONFLICT

대상은 존재하지만 expected revision이 현재 서버 revision과 다름.

## 409 DELETED_CONFLICT

클라이언트가 가진 대상이 서버에서 이미 삭제됨.

## 409 OPERATION_ID_REUSED

동일 operationId를 다른 payload에 재사용함.

## 422 VALIDATION_ERROR

금액, 날짜, 참조 무결성 등 도메인 검증 실패.

## 5xx

서버 내부 실패.

5xx 응답에서는 mutation이 적용되었는지 불명확할 수 있으므로 클라이언트는 새로운 operationId를 만들지 않고 기존 operationId로 결과를 재확인한다.

---

# 16. 저장 성공 UI 규칙

서버 성공 응답 전에는:

- 등록 모달을 완료 상태로 닫지 않는다.
- “저장 완료”를 표시하지 않는다.
- pending 작업을 성공 처리하지 않는다.

서버 성공 응답에는 가능한 한 다음 정보를 포함한다.

- operationId
- entity id
- 최종 revision
- 변경된 서버 정본 또는 필요한 최소 정본 데이터
- 관련 sync 정보가 필요한 경우 해당 정보

mutation 성공 뒤 전체 snapshot을 다시 읽는 대신 응답받은 대상 데이터를 현재 client server state에 반영한다.

---

# 17. 동기화 실행 시점

다른 기기 변경을 장시간 모르고 있는 상태를 정상으로 간주하지 않는다.

sync는 적어도 다음 시점에서 검토한다.

- 앱 최초 진입
- 앱이 다시 foreground가 됨
- 네트워크 재연결
- mutation 성공 후 필요한 경우
- 일정한 활성 사용 구간
- 사용자의 명시적 새로고침
- full resync 복구

실제 구현이 polling, event 기반 또는 다른 방식인지와 관계없이 최종 수렴 조건을 만족해야 한다.

---

# 18. 앱 종료·crash·네트워크 장애

다음 시나리오를 정상 설계 범위로 취급한다.

- mutation 요청 전 앱 종료
- 요청 전송 직후 앱 종료
- 서버 commit 후 응답 전에 앱 종료
- sync 응답 수신 중 crash
- 일부 change 적용 후 crash
- Wi-Fi ↔ LTE 전환
- timeout 후 늦은 응답
- 장시간 offline

이 상황에서 다음이 발생해서는 안 된다.

- 중복 거래
- 성공 거래 유실
- 삭제 거래 부활
- pending 사용자 입력 조용히 유실
- cursor가 실제 적용 위치보다 앞서감

---

# 19. D1 읽기 일관성

현재 저장 충돌 확인과 저장 직후 검증은 최신 서버 상태를 기준으로 한다.

향후 D1 read replication을 사용하는 경우:

- 충돌 판정
- mutation 직후 read
- 최신 revision 확인
- sync 정합성이 중요한 read

에서는 Session bookmark 또는 primary read 등 최신성을 보장하는 방식만 사용한다.

오래된 replica 값을 최신값으로 오인하지 않는다.

---

# 20. schema migration

스키마 변경은 배포 전에 검증된 D1 migration으로만 수행한다.

요청 처리 중 다음을 실행하지 않는다.

- `ALTER TABLE`
- 즉석 schema 생성
- 요청마다 migration 검사 후 구조 변경

revision, operation log, sync log, tombstone 구조 변경은 기존 정본 데이터의 의미를 보존해야 한다.

migration 전후 데이터 수, transaction ID, revision, 삭제 상태를 검증한다.

migration 실패 시 부분 완료 상태로 서비스를 계속 실행하지 않는다.

---

# 21. 동기화 완료 게이트

동기화 관련 기능은 다음 테스트를 통과하기 전 완료로 처리하지 않는다.

## 기본

- A 기기 등록 → B 기기 수신
- A 기기 수정 → B 기기 수신
- A 기기 삭제 → B 기기 삭제 반영
- 신규 기기 최초 bootstrap

## 동시 작업

- A/B 서로 다른 거래 동시 등록
- A/B 서로 다른 거래 동시 수정
- A/B 동일 거래 동시 수정
- A 수정 / B 삭제 동시 실행
- A 삭제 / B 수정 동시 실행

## 네트워크

- 요청 전 연결 끊김
- 요청 직후 연결 끊김
- 서버 성공 후 응답 유실
- 동일 operation 반복 재전송
- timeout 후 재시도
- 늦은 이전 응답 도착

## 오프라인

- B offline → A 수정 → B 복귀
- B offline 수정 → A 수정 → B 복귀
- B offline 수정 → A 삭제 → B 복귀
- B 하루 offline
- B 장기간 offline
- offline 중 여러 독립 거래 수정
- offline 중 동일 거래 여러 번 수정

## 삭제

- 삭제 후 오래된 클라이언트 복귀
- 삭제 후 오래된 mutation 전송
- tombstone/change log 이후 sync
- full resync 후 삭제 데이터가 다시 생기지 않음

## crash

- mutation 전 crash
- mutation 도중 crash
- 서버 commit 후 crash
- sync 도중 crash
- change 일부 적용 후 crash
- cursor 저장 직전 crash

## 복구

- cursor 손상
- change log 범위 초과
- full resync
- full resync 당시 pending operation 존재
- full resync 후 pending conflict

## 그룹 데이터

- 이체 수정·삭제
- 할부 그룹 동시 수정
- 할부 수정 중 충돌
- 정기기록 생성 중 규칙 변경
- 자산·카테고리 정렬 충돌
- 설정 키 독립 저장

각 테스트는 최소한 다음을 확인한다.

- 서버 최종 상태
- 각 클라이언트 최종 상태
- revision
- operationId 결과
- sync cursor
- 중복 발생 여부
- 데이터 유실 여부
- 삭제 부활 여부
- 충돌 UI
- 새로고침 후 상태
- 재접속 후 상태

하나라도 실패하면 동기화 작업을 완료 처리하지 않는다.

를 사용한다.

- `--d1=DB` 같은 로컬 D1 강제 인자
- `.wrangler` 데이터를 실데이터 판단 기준으로 사용
- localStorage를 실제 서버 데이터 대체로 사용

같은 포트에 이전 서버와 최신 서버를 동시에 실행하지 않는다.

# 26. UI/UX 기준

화면이 비슷해 보인다는 이유만으로 완료 처리하지 않는다.

영향받는 모든 상태를 확인한다.

## 공통

- 모드 전환 UI는 공통 모달 shell을 유지한다.
- 내부 form과 submit 처리만 변경한다.
- 모달을 닫고 별도 모달을 다시 여는 방식으로 모드를 전환하지 않는다.
- 동일 목적 컴포넌트는 화면마다 동일한 반경·테두리·간격·글자·아이콘·상태 규칙을 사용한다.
- 한 화면만 예외값으로 보정하지 않는다.

## 터치와 접근성

- 모바일 주요 조작 대상은 44px 이상을 목표로 한다.
- 압축 조작 대상은 40px 이상을 목표로 한다.
- 키보드 focus는 잘리지 않고 보여야 한다.
- 색상만으로 상태를 전달하지 않는다.
- 일반 텍스트 대비는 WCAG AA 수준을 목표로 한다.

## 정보 계층

화면마다 다음 우선순위가 명확해야 한다.

1. 제목
2. 현재 상태
3. 핵심 행동
4. 보조 행동

강조색은 현재 선택 상태와 단 하나의 주요 행동에 집중한다.

## 폼

- 사용자가 읽는 순서와 입력 순서를 일치시킨다.
- 필수 입력을 먼저 배치한다.
- 의미가 연결된 항목만 같은 행에 둔다.
- 모바일의 두 입력 한 행 배치는 의미와 터치 여유가 충분한 경우에만 허용한다.

통합 등록의 자산 모드는 예외 없이 다음을 각각 전체 폭 1행으로 배치한다.

- 카테고리
- 자산 이름
- 기초 금액
- 메모

거래 모드에서는 다음과 같이 의미가 밀접한 항목만 2분할할 수 있다.

- 날짜 / 시간
- 금액 / 할부

## 모달

모달은 한 가지 완료 목표만 가진다.

순서:

1. 제목
2. 모드
3. 본문
4. 하단 행동

모드 전환 시 제목과 하단 주요 행동 의미가 즉시 함께 변경되어야 한다.

## 저장 상태

- 저장 성공
- 저장 실패

오류는 문제, 해결 방법, 다음 행동을 입력 영역 가까이에 보여 준다.

## 레이아웃 단계와 상세 페이지

화면을 설계하거나 검증할 때는 아래 세 단계를 같은 기준으로 사용한다. 단계 판정은 이 순서로 하며, 화면별 임의 보정으로 다른 단계를 흉내 내지 않는다.

1. **PC**: 좌측 탭이 유지되는 데스크톱 레이아웃. 현재 기준으로 993px 이상을 사용한다.
2. **폴드**: PC가 아니면서 넓은 폴드·태블릿 비율을 가진 레이아웃. 현재 기준으로 `min-width: 540px` 및 `min-aspect-ratio: 3 / 4`를 사용한다.
3. **모바일**: PC·폴드 조건에 속하지 않는 손안의 세로 레이아웃.

자산 이력, 장부 이력처럼 누적량이 큰 상세 정보는 작은 모달 안에 계속 쌓지 않고 **상세 페이지 전환**으로 제공한다.

- 상세 페이지의 좌상단에는 `[<]` 뒤로가기 동작을 둔다. 뒤로가기는 이전 목록의 스크롤·필터·선택 상태를 보존한다.
- PC에서는 좌측 탭을 유지한 채 본문만 상세 페이지로 전환한다.
- 폴드와 모바일에서는 상단바·하단바를 유지한 채 본문만 상세 페이지로 전환한다.
- 상세 페이지의 제목, 뒤로가기, 본문 여백, loading·빈 상태·오류 상태는 세 단계에서 같은 컴포넌트 규칙을 사용한다.
- 긴 이력을 보기 위한 페이지 전환을 다시 별도 모달로 감싸거나, 화면 단계별로 독립적인 상세 레이아웃을 만들지 않는다.

# 27. UI 검증 범위

UI 변경은 기본 desktop 화면 하나로 완료하지 않는다. 페이지 전환·내비게이션·상세 이력 변경은 PC, 폴드, 모바일 세 단계에서 모두 확인한다.

최소 확인:

- 작은 모바일 폭
- 일반 모바일 폭
- desktop 폭
- 빈 값
- 긴 값
- 선택된 값
- 오류
- conflict
- 열린 dropdown
- 가상 키보드 상태
- loading
- 저장 중
- sync 중

dropdown은 실제 브라우저에서 위치, layer, 선택, 닫힘을 확인한다.

# 28. 변경 작업 규칙

- 변경은 사용자 요청 범위로 한정한다.
- 한글·이모지 텍스트 수정은 `apply_patch`로 수행한다.
- 작은 변경마다 `npm run build`를 실행한다.
- build 성공만으로 기능 완료 판정하지 않는다.
- 데이터 관련 변경은 반드시 실제 remote D1 상태까지 확인한다.
- 커밋·푸시는 사용자가 명시적으로 요청한 경우에만 수행한다.

의도적으로 요청되지 않는 한 다음 파일을 커밋하지 않는다.

- `.wrangler`
- `tsconfig.tsbuildinfo`
- 임시 backup
- runtime 생성 파일
- 로컬 테스트 DB

---

# 29. 완료 판정 금지 조건

다음 중 하나라도 해당하면 작업을 완료했다고 말하지 않는다.

- build만 성공하고 실제 동작을 확인하지 않음
- localStorage만 확인함
- local D1만 확인함
- UI 표시만 확인하고 서버 D1을 확인하지 않음
- mutation 성공만 확인하고 재시도를 확인하지 않음
- 정상 상황만 확인하고 conflict를 확인하지 않음
- 단일 기기만 확인하고 다중기기 영향을 무시함
- 삭제 후 장기 offline 복귀를 검증하지 않음
- sync cursor 적용을 확인하지 않음
- 다른 기기의 변경 수신을 확인하지 않음
- full resync 후 pending operation 보존을 확인하지 않음

---

# 30. 데이터 정책 변경 원칙

동기화·revision·operationId·sync cursor·삭제 처리 정책을 바꾸는 변경은 일반 기능 변경보다 위험도가 높다.

해당 영역을 수정할 때는:

1. 현재 불변조건 확인
2. 영향 저장 단위 확인
3. 기존 데이터 migration 영향 확인
4. failure scenario 작성
5. 구현
6. build
7. remote D1 검증
8. 다중기기 검증
9. offline 검증
10. 삭제 검증
11. retry 검증
12. hosted 환경 최종 검증

순서로 진행한다.

편의를 위해 데이터 무결성 규칙을 임시로 우회하지 않는다.

# 최종 원칙

MyWallet의 목표는 단순히 저장 요청이 성공하는 것이 아니다.

**PC, 모바일, 새 기기, 오래된 기기, 오프라인, 네트워크 timeout, 앱 강제 종료, 중복 요청, 동시 수정, 삭제가 섞여도 장부 데이터가 유실·중복·무단 덮어쓰기·삭제 부활 없이 서버 정본으로 수렴해야 한다.**

이를 만족하지 않는 구현은 기능이 동작해 보여도 완료된 구현으로 간주하지 않는다.
